# holoscan-recorder developer guide

## Layout

```text
recorder/
├── CMakeLists.txt               Standalone project against an installed Holoscan SDK 5.0
├── metadata.json                Module metadata (urn:holoscan:module:v2)
├── cmake/                       Package config template; the CLI template's Debian helper
├── include/holoscan/recorder/   Installed public API: format.hpp (no SDK), recorder_op.hpp, replayer_op.hpp
├── src/                         The format (format, csv, json, files: no SDK) and the operators
├── pkg/holoscan-recorder/       Debian packaging, entered when PKG_holoscan_recorder is ON
└── tests/
    ├── host/                    SDK-free tests of the format, built on their own by the Lint job
    └── installed_consumer/      Uses the installed package
```

The module follows the layout of the collection's other modules: public headers under `include/`,
one library for the public target, and the package config generated by the module itself, so that a
plain `cmake --install` produces a usable package. The Debian packaging keeps the CLI template's
`holohub_configure_deb()` and `PKG_holoscan_recorder` switch, so `holoscan package` works unchanged.

## Build and package boundary

| | |
| --- | --- |
| Build contexts | Top-level CMake project, or included by another project (`add_subdirectory()`, `FetchContent`, the repository root); it is not built inside the SDK tree |
| Options | Top level: `BUILD_TESTING` (`OFF`), `BUILD_SHARED_LIBS` (`ON`). Included: `HOLOSCAN_RECORDER_BUILD_TESTING` (`OFF`), always shared, the includer's `BUILD_TESTING` and `BUILD_SHARED_LIBS` left alone. Both: `PKG_holoscan_recorder` (`OFF`) |
| Public targets | `holoscan::recorder` (`libholoscan_recorder.so.1`) |
| Include root | `include/`, installed to `<prefix>/include` |
| Package | `<prefix>/lib/cmake/holoscan-recorder/holoscan-recorder-config.cmake`, `SameMajorVersion` |
| Consumer form | `find_package(holoscan-recorder)`; the install prefix on `CMAKE_PREFIX_PATH`, or `/usr` from the Debian package |
| Debian package | `holoscan-recorder`, all install rules, prefix `/usr`; depends on `holoscan (>= 5.0.0)` |
| External dependencies | Holoscan SDK 5.0 (`core`, `sensor_io`), the CUDA runtime. No compiled CUDA code, so no `CMAKE_CUDA_ARCHITECTURES` |
| Platforms | x86_64; aarch64 (Jetson Thor with JetPack 7, Jetson Orin with JetPack 7.2) |
| Test labels | `recorder`, and `gpu` or `host`; `data` on the tests that need `HOLOSCAN_TEST_DATA` |

## Conventions

- Code lives in `holoscan::recorder`. `format.hpp` and the sources behind it (`format.cpp`,
  `csv.cpp`, `json.cpp`, `files.cpp`) use only the standard library and POSIX, so that tools and the
  hosted tests use them without the SDK; keep SDK types out of them.
- A change to the on-disk format either stays readable by version 1 readers (a new column at the end
  is not: the header is checked exactly) or raises `version` in `recording.json`, and the reader
  keeps reading version 1.
- `RecorderOp::compute()` never waits for the disk: it copies into a slot of the writer's queue or
  drops. Anything that can block (file I/O, `cudaEventSynchronize` on a copy) belongs to the writer
  thread. Pinned memory is never freed while the graph runs, as `cudaFreeHost` synchronizes the
  device; a slot that grows retires its old buffer until `stop()`.
- The runtime may construct an operator more than once and calls `setup()` more than once: the
  constructors only check and read (the replayer reads the index, which gives its ports); files are
  created in `start()` and closed in `stop()`.
- Ports are made per stream at construction and stored behind `unique_ptr`, so they never move.
- A new field of `schema::ImageT` that a recording should keep needs a column, a case in
  `recorder_format`, and the round trip in `recorder_round_trip`. A new way a recording can be
  malformed needs a case in `recorder_malformed`.
