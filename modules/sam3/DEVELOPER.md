# holoscan-sam3 developer guide

## Layout

```text
sam3/
├── CMakeLists.txt             Standalone project against an installed Holoscan SDK 5.0
├── metadata.json              Module metadata (urn:holoscan:module:v2)
├── cmake/                     Package config template; the CLI template's Debian helper
├── include/holoscan/sam3/     Installed public API
├── src/                       The operators, their CUDA kernels, the prompt table, the host
│                              references, the stub model and the synthetic scene
├── tools/prepare_model.py     Exports SAM 3 with a separately installed PyTorch
├── pkg/holoscan-sam3/         Debian packaging, entered when PKG_holoscan_sam3 is ON
└── tests/
    ├── host/                  SDK-free tests, also a project of their own
    └── installed_consumer/    Uses the installed package
```

The layout follows the collection's other modules: public headers under `include/`, one library
per public target, and the package config generated by the module itself, so that a plain
`cmake --install` produces a usable package. The Debian packaging keeps the Holoscan CLI template's
`holohub_configure_deb()` and `PKG_holoscan_sam3` switch, so `holoscan package` works unchanged.

## Build and package boundary

| | |
| --- | --- |
| Build contexts | Top-level CMake project, or included by another project (`add_subdirectory()`, `FetchContent`, the repository root); it is not built inside the SDK tree |
| Options | Top level: `BUILD_TESTING` (`OFF`), `BUILD_SHARED_LIBS` (`ON`). Included: `HOLOSCAN_SAM3_BUILD_TESTING` (`OFF`), always shared, the includer's `BUILD_TESTING` and `BUILD_SHARED_LIBS` left alone. Both: `HOLOSCAN_SAM3_BUILD_OVERLAY`, `PKG_holoscan_sam3` (`OFF`); with tests, `HOLOSCAN_SAM3_MODEL_DIR` |
| Public targets | `holoscan::sam3` (`libholoscan_sam3.so.1`), `holoscan::sam3_overlay` (`libholoscan_sam3_overlay.so.1`, the `overlay` component) |
| Include root | `include/`, installed to `<prefix>/include` |
| Package | `<prefix>/lib/cmake/holoscan-sam3/holoscan-sam3-config.cmake`, `SameMajorVersion`; sets `holoscan-sam3_PREPARE_MODEL` |
| Consumer form | `find_package(holoscan-sam3 [COMPONENTS overlay])`; the install prefix on `CMAKE_PREFIX_PATH`, or `/usr` from the Debian package |
| Installed tool | `<prefix>/share/holoscan-sam3/prepare_model.py` |
| Debian package | `holoscan-sam3`, all install rules, prefix `/usr`; depends on `holoscan (>= 5.0.0)` |
| External dependencies | Holoscan SDK 5.0 (`core`, `sensor_io`, `inference`; `visualization` for the overlay; `testing` for the tests), the CUDA runtime, TensorRT 10 through HoloInfer |
| Platforms | x86_64; aarch64 (Jetson Thor and Orin, JetPack 7.2) |
| Test labels | `sam3` on all; `gpu` for the GPU tests; `host` for the SDK-free tests; `real_model` for the test that needs the export |

## Conventions

- Code lives in `holoscan::sam3`. Inside it, write the SDK's test harness as
  `holoscan::testing::...`; the tests' own helpers are `holoscan::sam3::test`.
- Public headers carry only SDK, CUDA runtime and standard types; HoloInfer stays private to
  `src/sam3_segmentation_op.cpp`. `pixel_math.hpp`, `prompts.hpp`, `reference.hpp`,
  `stub_model.hpp` and `synthetic_scene.hpp` need no CUDA, so `tests/host/` builds their sources
  without it.
- Every per-pixel expression of a kernel, and the ranking's comparison, lives in `pixel_math.hpp`,
  as a `__host__ __device__` function that the kernel and its host reference both call. The kernels
  are compiled without FMA contraction (`-fmad=false`), and the host code without
  `-ffp-contract`, so the tests compare them bit for bit. A new kernel computation goes there
  first.
- The operator binds the decoder's feature inputs to the encoder's HoloInfer output buffers, which
  TensorRT reads by address: keep the encoder's outputs and the decoder's first three inputs in the
  same order and shapes. `start()` checks both models' shapes against each other and the prompt
  table.
- The prompt table's format is written twice, in `src/prompts.cpp` and in
  `tools/prepare_model.py`; `prompts.hpp` describes it. Change both, and the format's magic, together.
- The stub model is the export's shapes in miniature: same tensor names and order, any sizes.
  The operator reads every size from the engines, so a test of a new behavior can use the stub.
- The repository holds no weights, and must not. `tools/prepare_model.py` runs the export in the
  user's own interpreter with the user's own Hugging Face token; tests use the stub model.
- A test that captures a GPU output with the SDK's harness passes a small capture capacity: the
  default of 1024 records sizes the output's GPU pool to 1024 images.
- A new setting or behavior of the operators needs a case in `sam3_operators`; a change to a
  kernel, a case in `sam3_kernels`.
