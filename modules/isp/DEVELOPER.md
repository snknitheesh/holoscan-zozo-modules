# holoscan-isp developer guide

## Layout

```text
isp/
├── CMakeLists.txt             Standalone project against an installed Holoscan SDK 5.0
├── metadata.json              Module metadata (urn:holoscan:module:v2)
├── cmake/                     Package config template; the CLI template's Debian helper
├── include/holoscan/isp/      Installed public API
├── src/                       The operator, the backends, the CUDA kernels; private headers
├── pkg/holoscan-isp/          Debian packaging, entered when PKG_holoscan_isp is ON
└── tests/
    ├── host/                  SDK-free tests of the settings and the CPU backend
    └── installed_consumer/    Uses the installed package
```

The module follows the layout of the collection's other modules: public headers under `include/`,
one library for the public target, and the package config generated by the module itself, so that a
plain `cmake --install` produces a usable package. The Debian packaging keeps the CLI template's
`holohub_configure_deb()` and `PKG_holoscan_isp` switch, so `holoscan package` works unchanged.

| Source | |
| --- | --- |
| `include/holoscan/isp/isp_params.hpp`, `src/isp_params.cpp` | Settings, views, the statistics layout, names, validation, tone tables. Plain C++ |
| `src/isp_math.hpp` | Every stage's per-pixel arithmetic, `__host__ __device__` under nvcc, plain C++ otherwise |
| `src/cpu_pipeline.{hpp,cpp}` | The CPU backend and the frame setup both backends share. Plain C++ |
| `src/cuda_pipeline.{hpp,cu}` | The CUDA backend: the fused tile kernel, the white balance and histogram passes |
| `include/holoscan/isp/isp_pipeline.hpp`, `src/isp_pipeline.cpp` | `IspPipeline`, which picks a backend |
| `include/holoscan/isp/isp_op.hpp`, `src/isp_op.cpp` | `IspOp`: checks and stages the raw image, allocates, runs, emits |
| `include/holoscan/isp/synthetic_raw*.hpp`, `src/synthetic_raw.{cpp,cu}` | The synthetic raw sensor and its truth |

## Build and package boundary

| | |
| --- | --- |
| Build contexts | Top-level CMake project, or included by another project (`add_subdirectory()`, `FetchContent`, the repository root); it is not built inside the SDK tree |
| Options | Top level: `BUILD_TESTING` (`OFF`), `BUILD_SHARED_LIBS` (`ON`). Included: `HOLOSCAN_ISP_BUILD_TESTING` (`OFF`), always shared, the includer's `BUILD_TESTING` and `BUILD_SHARED_LIBS` left alone. Both: `PKG_holoscan_isp` (`OFF`) |
| Public targets | `holoscan::isp` (`libholoscan_isp.so.1`) |
| Include root | `include/`, installed to `<prefix>/include` |
| Package | `<prefix>/lib/cmake/holoscan-isp/holoscan-isp-config.cmake`, `SameMajorVersion` |
| Consumer form | `find_package(holoscan-isp)`; the install prefix on `CMAKE_PREFIX_PATH`, or `/usr` from the Debian package |
| Debian package | `holoscan-isp`, all install rules, prefix `/usr`; depends on `holoscan (>= 5.0.0)` |
| External dependencies | Holoscan SDK 5.0 (`core`, `sensor_io`; `testing` for the tests), the CUDA runtime |
| Platforms | x86_64; aarch64 (Jetson Thor with JetPack 7, Jetson Orin with JetPack 7.2) |
| Test labels | `isp` and `gpu`; `isp` and `host` for the SDK-free ones |

## Conventions

- Code lives in `holoscan::isp`; what the backends share stays private in `holoscan::isp::detail`.
- The two backends must agree bit for bit. Every stage's arithmetic lives once, in
  `src/isp_math.hpp`, and both backends call it in the same order: a stage that one backend
  computes differently breaks `isp_pipeline`'s CUDA-against-CPU case. The library is compiled
  without contracting (`--fmad=false`, `-ffp-contract=off`), and so are the tests and the demo's
  checker, which evaluate the synthetic sensor on the host.
- The kernel's tile reflects coordinates at the image's edges (`mirror()`, keeping the mosaic's
  phase), and demosaics the sharpening's border pixels at their virtual coordinates; the CPU
  backend does the same, so edges match too.
- Statistics are deterministic: the sums are integers in units of 2^-20 and the histograms integer
  counts, so the order of the atomics does not matter. A new statistic must keep that.
- Transcendental functions stay out of the per-pixel path: the tone curves are tables built on the
  host. Only the auto-exposure suggestion uses `log2` and `exp2`, and the tests allow its last bits.
- Host memory reaches the GPU on a stream that is then waited for, never through a plain
  `cudaMemcpy` from pageable memory, which may return before its data has landed while the frames'
  non-blocking streams would not wait for it.
- An operator has an optional port only when configured: an emit into an unconnected output fails.
  A refused emit cannot be retried, as the loan is gone; it fails the frame.
- A new stage or setting needs a case in `isp_pipeline` against the truth or the arithmetic, and in
  the CUDA-against-CPU list; a new port or input form of the operator, a case in `isp_op`.
