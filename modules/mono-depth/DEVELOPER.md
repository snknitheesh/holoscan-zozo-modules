# holoscan-mono-depth developer guide

## Layout

```text
mono-depth/
├── CMakeLists.txt                Standalone project against an installed Holoscan SDK 5.0
├── metadata.json                 Module metadata (urn:holoscan:module:v2)
├── cmake/                        Package config template; the CLI template's Debian helper
├── include/holoscan/mono_depth/  Installed public API
├── src/                          The operator, its CUDA kernels, the host references, the stub
│                                 model and the synthetic scene
├── tools/prepare_model.py        Exports Depth Anything V2 with a separately installed PyTorch
├── pkg/holoscan-mono-depth/      Debian packaging, entered when PKG_holoscan_mono_depth is ON
└── tests/
    ├── host/                     SDK-free tests, also a project of their own
    └── installed_consumer/       Uses the installed package
```

The layout follows the collection's other modules: public headers under `include/`, one library
per public target, and the package config generated by the module itself, so that a plain
`cmake --install` produces a usable package. The Debian packaging keeps the Holoscan CLI template's
`holohub_configure_deb()` and `PKG_holoscan_mono_depth` switch, so `holoscan package` works
unchanged.

## Build and package boundary

| | |
| --- | --- |
| Build contexts | Top-level CMake project, or included by another project (`add_subdirectory()`, `FetchContent`, the repository root); it is not built inside the SDK tree |
| Options | Top level: `BUILD_TESTING` (`OFF`), `BUILD_SHARED_LIBS` (`ON`). Included: `HOLOSCAN_MONO_DEPTH_BUILD_TESTING` (`OFF`), always shared, the includer's `BUILD_TESTING` and `BUILD_SHARED_LIBS` left alone. Both: `PKG_holoscan_mono_depth` (`OFF`); with tests, `HOLOSCAN_MONO_DEPTH_MODEL` |
| Public target | `holoscan::mono_depth` (`libholoscan_mono_depth.so.1`) |
| Include root | `include/`, installed to `<prefix>/include` |
| Package | `<prefix>/lib/cmake/holoscan-mono-depth/holoscan-mono-depth-config.cmake`, `SameMajorVersion`; sets `holoscan-mono-depth_PREPARE_MODEL` |
| Consumer form | `find_package(holoscan-mono-depth)`; the install prefix on `CMAKE_PREFIX_PATH`, or `/usr` from the Debian package |
| Installed tool | `<prefix>/share/holoscan-mono-depth/prepare_model.py` |
| Debian package | `holoscan-mono-depth`, all install rules, prefix `/usr`; depends on `holoscan (>= 5.0.0)` |
| External dependencies | Holoscan SDK 5.0 (`core`, `sensor_io`, `inference`; `testing` for the tests), the CUDA runtime, TensorRT 10 through HoloInfer |
| Platforms | x86_64; aarch64 (Jetson Thor and Orin, JetPack 7.2) |
| Test labels | `mono_depth` on all; `gpu` for the GPU tests; `host` for the SDK-free tests; `real_model` for the test that needs the exported model |

## Conventions

- Code lives in `holoscan::mono_depth`. Inside it, write the SDK's test harness as
  `holoscan::testing::...`; the tests' own helpers are `holoscan::mono_depth::test`.
- Public headers carry only SDK, CUDA runtime and standard types; HoloInfer stays private to
  `src/mono_depth_op.cpp`. `image_fit.hpp`, `pixel_math.hpp`, `colormap.hpp`, `reference.hpp`,
  `stub_model.hpp` and `synthetic_scene.hpp` need no CUDA, so `tests/host/` builds their sources
  without it.
- Every per-pixel expression of a kernel lives in `pixel_math.hpp`, as a `__host__ __device__`
  function that the kernel and its host reference both call. The kernels are compiled without FMA
  contraction (`-fmad=false`), and the host code without `-ffp-contract`, so the tests compare them
  bit for bit. A new kernel computation goes there first.
- The Turbo table is one macro in `colormap.hpp` that initializes both the host array and the
  kernels' constant memory, so the two cannot drift.
- The repository holds no weights, and must not. `tools/prepare_model.py` runs the export in the
  user's own interpreter; tests use the stub model.
- A test that captures a GPU output with the SDK's harness passes a small capture capacity: the
  default of 1024 records sizes the output's GPU pool to 1024 images.
- A new setting or behavior of the operator needs a case in `mono_depth_operators`; a change to a
  kernel, a case in `mono_depth_kernels`.
