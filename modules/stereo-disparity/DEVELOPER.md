# holoscan-stereo-disparity developer guide

## Layout

```text
stereo-disparity/
├── CMakeLists.txt                      Standalone project against an installed Holoscan SDK 5.0
├── metadata.json                       Module metadata (urn:holoscan:module:v2)
├── cmake/                              Package config template; the CLI template's Debian helper
├── include/holoscan/stereo_disparity/  Installed public API
├── src/                                The operator, the VPI matcher, CUDA kernels; private headers
├── pkg/holoscan-stereo-disparity/      Debian packaging, entered when PKG_holoscan_stereo_disparity is ON
└── tests/
    ├── host/                           SDK-free tests, also a project of their own
    └── installed_consumer/             Uses the installed package
```

The layout follows the repository's other modules: public headers under `include/`, one library
for the one public target, and the package config generated by the module, so that a plain
`cmake --install` gives a usable package. The Debian packaging keeps the CLI template's
`holohub_configure_deb()` and `PKG_holoscan_stereo_disparity` switch.

## How a frame runs

1. `LatestCameraInfo::update()` takes the camera info the contract selected; without one yet, the
   frame is skipped. When it changed, the depth's camera info is computed again
   (`depth_camera_info()`).
2. The pair is checked, and the camera info against it (`camera_info_problem()`). On the
   operator's own CUDA stream (the work stream): device images' producers are waited for, host
   images are copied to the GPU, and the stream waits for the last frame's outputs to have read the
   matcher's result. VPI has nothing queued then, so this is allowed.
3. `Matcher::match()` runs the frame and leaves the result in the matcher's own buffers:
   - `cuda` and `ofa` queue it on a VPI stream that wraps the work stream, so the GPU and the OFA
     run it in the order it is queued, after the work stream's own work, and wait once
     (`vpiStreamSync`), which VPI's rule for a wrapped stream needs before the stream is used again.
     `cuda` matches MONO8 device images in place, wrapped for VPI; VPI's CUDA backend converts
     color to gray first, and writes the result into the matcher's buffers.
   - `ofa` and `pva` need block-linear gray, which VPI's CUDA backend writes from color directly.
     MONO8 is expanded to RGBA8 by a kernel first: VPI 4.1.4 has no CUDA conversion from gray to
     block-linear, and the VIC's is slower (3.6 ms against 0.2 ms per 1280x720 image on Thor).
   - `ofa`'s disparity is block-linear, which VPI 4.1.4's CUDA backend cannot convert. After
     `vpiStreamSync`, the matcher locks it for CUDA (VPI converts it on CUDA, 0.07 ms at 1280x720 on
     Thor, where the VIC took 2.6 ms), copies it on the work stream, waits, and unlocks it: VPI may
     move the memory once unlocked, and a pointer kept past the unlock read wrong pixels.
   - `pva` runs on a VPI stream of its own. On Jetson Thor, VPI 4.1.4 loses the PVA's result on a
     stream that wraps a CUDA stream: in CI, CUDA read it unwritten (all zero) whether VPI's CUDA
     backend copied it on the stream, the host waited between the conversion and the PVA, or it was
     read through a lock, in most sizes and settings, while Orin was right. On its own stream it is
     right everywhere. So the host waits for the work stream first, and VPI converts, matches,
     copies the result into the matcher's buffers and is waited for once.
4. One kernel reads those buffers and writes the outputs on the runtime's stream: disparity, depth
   and confidence, into runtime-pool outputs. The operator does not wait for it; an event after it
   orders the next frame's matching. The depth's camera info, stamped with the frame's capture
   time, goes out before the depth.

Per frame, that is one host wait on `cuda` and two on `ofa` and `pva`; no copy of the pair, only
the conversions VPI needs (color to gray on `cuda`; to block-linear on `ofa` and `pva`, and back on
`ofa`), the MONO8 expansion on `ofa` and `pva`, the copy of host images to the GPU, and on `ofa`
and `pva` the copy of the result out of VPI's images. On x86_64, a trace of the demo's `cuda`
backend (Nsight Systems) shows the operator's thread with one `cudaStreamSynchronize`, from
`vpiStreamSync`, and no copy per frame.

The runtime's CUDA stream is shared by the operators of an execution partition (by default, SDK
5.0 gives each partition one), so the operator never waits for it on the host: that would wait for
the other operators' work too.

## Conventions

- Code lives in `holoscan::stereo_disparity`. VPI's C API stays in `src/`; public headers carry
  only SDK, CUDA runtime and standard types, and the operator keeps its state behind a pointer.
- The camera info is holoscan-messages' (`holoscan::messages`); the module defines no message of
  its own.
- `Backend::kAuto` is not a backend: `resolve_auto()` maps it, from `PlatformFacts`, the
  parameters and the image size, to one that is, and `available_backends()` never lists it. The
  rules are in `disparity_options.cpp`, which needs no SDK, so `stereo_disparity_options` covers
  them with injected facts; `probe_platform()` gathers the real ones from VPI.
- Every VPI constraint the operator relies on is checked by `params_problem()` or `size_problem()`
  before VPI sees it, with a message naming the parameter; VPI's own errors are reported with its
  status name and message.
- Logging goes through `HOLOSCAN_LOG_*`. Nothing is logged per frame: the host-to-device copy and
  `auto`'s choice are logged once.
- The CMake project must also work inside another one: only its own paths, options other than the
  standard ones prefixed `HOLOSCAN_STEREO_DISPARITY_`, and
  `HOLOSCAN_STEREO_DISPARITY_BUILD_TESTING`, never `BUILD_TESTING`, to decide whether to build the
  tests.
- A new backend or parameter needs its rule in `disparity_options.cpp` and a case in both tests.
- A default that depends on the backend or the platform is an unset `std::optional` field,
  resolved by a function next to the rules (`include_diagonals_for()`, `num_passes_for()`). A
  default changes only on measured numbers, which go into the README's Defaults table.
