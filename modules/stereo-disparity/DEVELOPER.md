# holoscan-stereo-disparity developer guide

## Layout

```text
stereo-disparity/
├── CMakeLists.txt                      Standalone project against an installed Holoscan SDK 5.0
├── metadata.json                       Module metadata (urn:holoscan:module:v2)
├── cmake/                              Package config template; the CLI template's Debian helper
├── include/holoscan/stereo_disparity/  Installed public API
├── schemas/                            The StereoGeometry FlatBuffers schema
├── src/                                The operator, the VPI matcher, CUDA kernels; private headers
├── pkg/holoscan-stereo-disparity/      Debian packaging, entered when PKG_holoscan_stereo_disparity is ON
└── tests/
    ├── host/                           SDK-free tests, also a project of their own
    └── installed_consumer/             Uses the installed package
```

The layout follows the repository's other modules: public headers under `include/`, one library
for the one public target, and the package config generated by the module, so that a plain
`cmake --install` gives a usable package. The Debian packaging keeps the CLI template's
`holohub_configure_deb()` and `PKG_holoscan_stereo_disparity` switch.

## Build and package boundary

| | |
| --- | --- |
| Build contexts | Standalone top-level CMake project; or inside another project through `add_subdirectory()` or `FetchContent`, where its target is used as `holoscan::stereo_disparity` |
| Options | Standalone: `BUILD_TESTING` (`OFF`) and `BUILD_SHARED_LIBS` (`ON`). Inside another project those two are the project's and are left alone: the module sets `BUILD_SHARED_LIBS` `ON` in its own scope and builds its tests only with `HOLOSCAN_STEREO_DISPARITY_BUILD_TESTING` (`OFF`). Both: `PKG_holoscan_stereo_disparity` (`OFF`) |
| Public target | `holoscan::stereo_disparity` (`libholoscan_stereo_disparity.so.1`) |
| Include root | `include/`, installed to `<prefix>/include`; the generated `stereo_geometry_*` headers install beside the others in `holoscan/stereo_disparity/` |
| Package | `<prefix>/lib/cmake/holoscan-stereo-disparity/holoscan-stereo-disparity-config.cmake`, `SameMajorVersion` |
| Debian package | `holoscan-stereo-disparity`, all install rules, prefix `/usr`; depends on `holoscan (>= 5.0.0)` and `libnvvpi4 (>= 4.0)` |
| External dependencies | Holoscan SDK 5.0 (`core`, `sensor_io`; `testing` for the tests), the CUDA runtime, VPI 4 (required, linked privately) |
| Test labels | `stereo_disparity` on all; `gpu` for the GPU test; `host` for the SDK-free test |

## How a frame runs

1. The pair (and the geometry) are checked; device images wait for their producer on the
   operator's own CUDA stream, host images on the host.
2. On that stream, host images are copied to the GPU, and both are converted to gray, straight into
   VPI's images (`Y8_ER`, locked for CUDA). The operator waits for its stream.
3. `Matcher::match()` submits the estimator on a VPI stream and waits for it. `ofa` and `pva`
   convert the pair to block-linear with VIC first; `ofa` converts its block-linear disparity back.
4. VPI's raw Q10.5 disparity (and confidence) is copied out on the operator's stream, so VPI's
   images are unlocked before the outputs are written, and the operator waits for that copy.
5. One kernel writes the outputs on the runtime's stream: disparity, depth and confidence. The
   operator does not wait for it; the next frame's copy waits for it on the GPU.

The runtime's CUDA stream is shared by the operators of a graph, so the operator never waits for
it on the host: that would wait for the other operators' work too.

## Conventions

- Code lives in `holoscan::stereo_disparity`. VPI's C API stays in `src/`; public headers carry
  only SDK, CUDA runtime and standard types, and the operator keeps its state behind a pointer.
- Inside `holoscan::stereo_disparity`, `schema::` means this module's FlatBuffers namespace; write
  the SDK's schemas as `holoscan::schema::...`.
- `Backend::kAuto` is not a backend: `resolve_auto()` maps it, from `PlatformFacts`, the
  parameters and the image size, to one that is, and `available_backends()` never lists it. The
  rules are in `disparity_options.cpp`, which needs no SDK, so `stereo_disparity_options` covers
  them with injected facts; `probe_platform()` gathers the real ones from VPI.
- Every VPI constraint the operator relies on is checked by `params_problem()` or `size_problem()`
  before VPI sees it, with a message naming the parameter; VPI's own errors are reported with its
  status name and message.
- Logging goes through `HOLOSCAN_LOG_*`. Nothing is logged per frame: the host-to-device copy and
  `auto`'s choice are logged once.
- The CMake project must also work inside another one: only its own paths, options other than the
  standard ones prefixed `HOLOSCAN_STEREO_DISPARITY_`, and
  `HOLOSCAN_STEREO_DISPARITY_BUILD_TESTING`, never `BUILD_TESTING`, to decide whether to build the
  tests.
- A new backend or parameter needs its rule in `disparity_options.cpp` and a case in both tests.
