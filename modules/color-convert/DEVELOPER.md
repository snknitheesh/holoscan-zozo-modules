# holoscan-color-convert developer guide

## Layout

```text
color-convert/
├── CMakeLists.txt                   Standalone project against an installed Holoscan SDK 5.0
├── metadata.json                    Module metadata (urn:holoscan:module:v2)
├── cmake/                           Package config template; the CLI template's Debian helper
├── include/holoscan/color_convert/  Installed public API
├── src/                             Operators, the Converter, the kernel, the VIC; private headers
├── pkg/holoscan-color-convert/      Debian packaging, entered when PKG_holoscan_color_convert is ON
└── tests/
    ├── host/                        SDK-free tests, also a project of their own
    └── installed_consumer/          Uses the installed package
```

The layout and CMake follow the repository's other modules (see `modules/apriltag`): public
headers under `include/`, one library, the package config generated by the module, and the CLI
template's `holohub_configure_deb()` behind `PKG_holoscan_color_convert`.

## Build and package boundary

| | |
| --- | --- |
| Build contexts | Standalone top-level CMake project; or inside another project through `add_subdirectory()` or `FetchContent`, where its target is used as `holoscan::color_convert` |
| Options | Standalone: `BUILD_TESTING` (`OFF`) and `BUILD_SHARED_LIBS` (`ON`). Inside another project those two are the project's and are left alone: the module sets `BUILD_SHARED_LIBS` `ON` in its own scope and builds its tests only with `HOLOSCAN_COLOR_CONVERT_BUILD_TESTING` (`OFF`). Both: `HOLOSCAN_COLOR_CONVERT_WITH_VPI` (`ON`), `PKG_holoscan_color_convert` (`OFF`) |
| Public target | `holoscan::color_convert` (`libholoscan_color_convert.so.1`) |
| Include root | `include/`, installed to `<prefix>/include` |
| Package | `<prefix>/lib/cmake/holoscan-color-convert/holoscan-color-convert-config.cmake`, `SameMajorVersion`; sets `holoscan-color-convert_WITH_VPI` |
| Debian package | `holoscan-color-convert`, all install rules, prefix `/usr`; depends on `holoscan (>= 5.0.0)` and, with VPI, `libnvvpi4 (>= 4.0)` |
| External dependencies | Holoscan SDK 5.0 (`core`, `sensor_io`; `testing` for the tests), the CUDA runtime, VPI 4 (optional) |
| Platforms | x86_64; aarch64 (Jetson Thor and Orin, JetPack 7) |
| Test labels | `color_convert` on all; `gpu` for the GPU tests; `host` for the SDK-free tests |

## How it fits together

- `pixel_format.hpp`, `image_view.hpp`, `conversion.hpp` and `backend.hpp` are SDK- and CUDA-free:
  the formats and their layout, a borrowed image, what a conversion does and its geometry, and the
  backend choice. `src/conversion.cpp` implements them.
- `src/kernel_math.hpp` is the arithmetic of one destination block (a pixel, or the pixels that
  share a chroma sample): decode, sample, convert, encode. The CUDA kernel (`src/kernels.cu`) and
  the CPU reference (`src/reference.cpp`) both call it, and both are compiled without
  floating-point contraction (`--fmad=false`, `-ffp-contract=off`), so they round alike and agree
  to the byte. Change the arithmetic there, never in one of them alone.
- `make_plan()` turns a conversion into plain values for the kernel: the source rectangle, the
  scale, the content rectangle, one 3x4 affine map from the source's colour model to the
  destination's (computed in double precision from the luma weights, identity within a model),
  and the fill colour already in the destination's model.
- `Converter` (`converter.hpp`) runs a conversion on CUDA or the VIC and resolves `auto`.
  `src/vic.cpp`, built only with VPI, wraps the CUDA images as VPI images (a crop or a content
  rectangle as a sub-image at an offset: VPI's image views crash the VIC when their parent wraps
  CUDA memory) and uses `vpiSubmitConvertImageFormat` for a same-size conversion between formats
  and `vpiSubmitRescale` for everything else. `src/vic_unavailable.cpp` stands in without VPI.
- `src/op_support.cpp` is what both operators share: reading an `ImageT` into a view, staging host
  images, choosing and logging the backend, and publishing the result with its descriptor.

## Conventions

- Public headers carry only SDK, CUDA runtime and standard types; the SDK-free ones carry none of
  the SDK or CUDA, so `tests/host/` builds them without either.
- A new format needs: its `PixelFormat` and `format_info()`, `load()`, `store()` and, for YUV,
  `store_chroma()` in `kernel_math.hpp`, its encoding in `op_support.cpp`, and the tests'
  `textbook.hpp` reader and writer. The every-pair tests then cover it against every other format.
- What the VIC can do is `vic_limitation()`, which `auto`, the `vic` backend's checks and the
  parity test all use. Measure before widening it: VPI drops a backend from an image whose format
  that backend cannot use, rather than failing, and the wrapper refuses such images.
- Logging goes through `HOLOSCAN_LOG_*`, and nothing per frame: the host copy is logged once, and
  `auto`'s choice when it is made or changes.
- The CMake project must also work inside another one: only its own paths, options other than the
  standard ones prefixed `HOLOSCAN_COLOR_CONVERT_`, and `HOLOSCAN_COLOR_CONVERT_BUILD_TESTING`,
  never `BUILD_TESTING`, to decide whether to build the tests.

## Benchmark

`color_convert_benchmark`, built with the tests, prints the README's table for the machine it runs
on, `cuda` and, where VPI reports a VIC, `vic`:

```bash
build/color-convert/tests/color_convert_benchmark [calls]   # default 200 calls a round
```

On a Jetson, run it in the CI image with `--runtime nvidia --privileged`, on an idle board: the GPU
and the VIC scale their clocks with load. `COLOR_CONVERT_PARITY_VERBOSE=1` makes
`color_convert_vic_parity_test` print the difference of every conversion it compares.
