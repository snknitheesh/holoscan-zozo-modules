# holoscan-apriltag developer guide

## Layout

```text
apriltag/
├── CMakeLists.txt              Standalone project against an installed Holoscan SDK 5.0
├── metadata.json               Module metadata (urn:holoscan:module:v2)
├── cmake/                      Package config template; the CLI template's Debian helper
├── include/holoscan/apriltag/  Installed public API
├── schemas/                    The AprilTagDetections FlatBuffers schema
├── src/                        Operators, backends, CUDA kernels; private headers
├── pkg/holoscan-apriltag/      Debian packaging, entered when PKG_holoscan_apriltag is ON
└── tests/
    ├── host/                   SDK-free tests, also a project of their own
    └── installed_consumer/     Uses the installed package
```

The skeleton came from `holoscan create apriltag --language cpp` (holoscan-cli 5.0.0), reshaped
into the compact layout of the SDK's own modules: public headers under `include/`, one library per
public target instead of one per operator directory, and the package config generated by the
module itself, so that a plain `cmake --install` produces a usable package. The Debian packaging
keeps the template's `holohub_configure_deb()` and `PKG_holoscan_apriltag` switch, so
`holoscan package` works unchanged.

## Build and package boundary

| | |
| --- | --- |
| Build contexts | Standalone top-level CMake project only; it is not built inside the SDK tree |
| Options | `BUILD_TESTING` (`OFF`), `HOLOSCAN_APRILTAG_WITH_VPI` (`ON`), `HOLOSCAN_APRILTAG_BUILD_OVERLAY` (`ON`), `PKG_holoscan_apriltag` (`OFF`), `BUILD_SHARED_LIBS` (`ON`) |
| Public targets | `holoscan::apriltag` (`libholoscan_apriltag.so.1`), `holoscan::apriltag_overlay` (`libholoscan_apriltag_overlay.so.1`) |
| Include root | `include/`, installed to `<prefix>/include`; the generated `apriltag_detections_*` headers install beside the others in `holoscan/apriltag/` |
| Package | `<prefix>/lib/cmake/holoscan-apriltag/holoscan-apriltag-config.cmake`, `SameMajorVersion` |
| Consumer form | `find_package(holoscan-apriltag [COMPONENTS overlay])`; the install prefix on `CMAKE_PREFIX_PATH`, or `/usr` from the Debian package |
| Debian package | `holoscan-apriltag`, all install rules, prefix `/usr`; depends on `holoscan (>= 5.0.0)` and, with VPI, `libnvvpi4 (>= 4.0)` |
| External dependencies | Holoscan SDK 5.0 (`core`, `sensor_io`; `visualization` for the overlay; `testing` for the tests), the CUDA runtime, AprilTag 3 (installed, or 3.4.5 fetched, built static and hidden inside the library), VPI 4 (optional) |
| Platforms | x86_64; aarch64 (Jetson Thor, JetPack 7) |
| Test labels | `apriltag` on all; `gpu` for the GPU tests; `host` for the SDK-free test |

## Conventions

- Code lives in `holoscan::apriltag`. AprilTag 3's C API stays in the `.cpp` and `.cu` files and
  its symbols stay inside the library. Do not name a namespace or a type after one of its global C
  names (`apriltag_detection`, `apriltag_family`, ...): they clash.
- Inside `holoscan::apriltag`, `schema::` means this module's FlatBuffers namespace
  (`holoscan::apriltag::schema`); write the SDK's schemas as `holoscan::schema::...`.
- Public headers carry only SDK, CUDA runtime and standard types. Backend, CUDA-kernel and
  AprilTag 3 details stay private in `src/`; `AprilTagDetectorOp` keeps its state behind a pointer
  for the same reason.
- Device code uses CCCL headers available in CUDA 13.0 (CUB, `thrust::counting_iterator`), so the
  module also builds with JetPack 7's toolkit.
- The CUDA quad fit and decoder are compiled without FMA contraction (`--fmad=false`), so they
  round as the CPU reference does.
- A new backend or option needs a case in `apriltag_backend_accuracy`; a new port or behavior of an
  operator, a case in `apriltag_operators`.
