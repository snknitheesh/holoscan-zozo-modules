# holoscan-fiducials developer guide

## Layout

```text
fiducials/
├── CMakeLists.txt                Standalone project against an installed Holoscan SDK 5.0
├── metadata.json                 Module metadata (urn:holoscan:module:v2)
├── cmake/                        Package config template; the CLI template's Debian helper
├── include/holoscan/fiducials/   Installed public API
├── schemas/                      The FiducialDetections FlatBuffers schema
├── src/                          Operators, backends, CUDA kernels; private headers
├── tools/                        generate_dictionaries.py, which writes src/dictionary_codes.cpp
├── pkg/holoscan-fiducials/       Debian packaging, entered when PKG_holoscan_fiducials is ON
└── tests/
    ├── host/                     SDK-free tests, also a project of their own
    └── installed_consumer/       Uses the installed package
```

The layout and build are those of `holoscan-apriltag`: public headers under `include/`, one
library per public target, the package config generated by the module itself, and the CLI
template's `holohub_configure_deb()` behind `PKG_holoscan_fiducials`.

## Build and package boundary

| | |
| --- | --- |
| Build contexts | Standalone top-level CMake project; or inside another project through `add_subdirectory()` or `FetchContent`, where its targets are used as `holoscan::fiducials` and `holoscan::fiducials_overlay` |
| Options | Standalone: `BUILD_TESTING` (`OFF`) and `BUILD_SHARED_LIBS` (`ON`). Inside another project those two are left alone, and the tests need `HOLOSCAN_FIDUCIALS_BUILD_TESTING` (`OFF`). Both: `HOLOSCAN_FIDUCIALS_BUILD_OVERLAY` (`ON`, or `OFF` when `HOLOSCAN_ZOZO_MODULES_OPERATORS` is defined without `FiducialOverlayOp`), `PKG_holoscan_fiducials` (`OFF`) |
| Public targets | `holoscan::fiducials` (`libholoscan_fiducials.so.1`), `holoscan::fiducials_overlay` (`libholoscan_fiducials_overlay.so.1`) |
| Include root | `include/`, installed to `<prefix>/include`; the generated `fiducial_detections_*` headers install beside the others in `holoscan/fiducials/` |
| Package | `<prefix>/lib/cmake/holoscan-fiducials/holoscan-fiducials-config.cmake`, `SameMajorVersion` |
| External dependencies | Holoscan SDK 5.0 (`core`, `sensor_io`; `visualization` for the overlay; `testing` for the tests) and the CUDA runtime |
| Test labels | `fiducials` on all; `gpu` for the GPU tests; `host` for the SDK-free ones |

## How detection is shared

[`src/detection_core.hpp`](src/detection_core.hpp) holds every step, compiled for the host and the
device. The CPU backend ([`src/cpu_detector.cpp`](src/cpu_detector.cpp)) and the CUDA backend
([`src/cuda_backend.cu`](src/cuda_backend.cu)) only loop over pixels, tiles, candidates and
chessboard corners differently:

- Per-pixel steps (threshold, components, the four quad passes) are integer or exactly ordered:
  component roots are each component's lowest pixel index, and the quad passes keep the maximum of
  keys that break ties by pixel index, so the order threads reach them does not matter.
- Per-candidate and per-corner steps run on 32 lanes: a warp on the GPU (`WarpLanes`), a loop on
  the CPU (`core::SerialLanes`). Each lane takes its share (edge samples, cells, dictionary markers,
  window pixels), and the shares are added in the warp butterfly's order on both. Run serially in
  one GPU thread, these steps took ten times as long as on the CPU.
- No transcendental functions run in either backend, and the library is built without FMA
  contraction (`--fmad=false` for device code, `-ffp-contract=off` for all host code), so both
  round alike. It must be the whole library: the core's inline functions are emitted by every file
  that uses them, and the linker keeps any one copy.

`fiducials_backends` checks the result: the same markers, corners and chessboard corners, to the bit.
A change to `detection_core.hpp` must keep it so. The one exception is a frame with more than 4096
candidates: the CPU examines the first in scan order, the GPU whichever its threads reach first, so
which markers such a frame misses differs, and on the GPU from run to run.

## Conventions

- Code lives in `holoscan::fiducials`; inside it, `schema::` means this module's FlatBuffers
  namespace, and the SDK's schemas are written `holoscan::schema::...`.
- Public headers carry only SDK, CUDA runtime and standard types. `types.hpp`, `dictionary.hpp`,
  `charuco.hpp`, `pose.hpp`, `synthetic_scene.hpp` and `overlay_drawing.hpp` need neither the SDK
  nor CUDA, so the host tests build them, with the CPU detector, from source.
- Logging goes through `HOLOSCAN_LOG_*`. Nothing is logged per frame: a host/device copy is logged
  once, capacity warnings at most every five seconds.
- The CMake project must also work inside another one: only its own paths, options other than the
  standard ones prefixed `HOLOSCAN_FIDUCIALS_`, and `HOLOSCAN_FIDUCIALS_BUILD_TESTING` to decide
  whether to build the tests.
- `Backend::kAuto` is not a backend: `resolve_auto()` maps it, from `PlatformFacts`, to one that is.
- A new option or behavior of the detector needs a case in the host tests and, if it touches the
  GPU, in `fiducials_backends`' parity scenes; a new port or behavior of an operator, a case in
  `fiducials_operators`.

## The dictionary tables

`src/dictionary_codes.cpp` is generated; do not edit it. To regenerate it, in an environment with
the pinned OpenCV:

```bash
python3 -m pip install opencv-python-headless==4.12.0.88
python3 modules/fiducials/tools/generate_dictionaries.py > modules/fiducials/src/dictionary_codes.cpp
```

The tool reads each marker by rendering it one pixel per cell, so the bits are the printed ones,
checks that the 50, 100 and 250 marker dictionaries are prefixes of the 1000 marker ones, turns
OpenCV's AprilTag tags back the half turn OpenCV adds, and computes the AprilTag families'
correction from their distances. `fiducials_dictionary` pins a few codes against OpenCV's and the
AprilTag library's own renderings.
