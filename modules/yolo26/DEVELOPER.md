# holoscan-yolo26 developer guide

## Layout

```text
yolo26/
├── CMakeLists.txt              Standalone project against an installed Holoscan SDK 5.0
├── metadata.json               Module metadata (urn:holoscan:module:v2)
├── cmake/                      Package config template; the CLI template's Debian helper
├── include/holoscan/yolo26/    Installed public API
├── src/                        Operators, CUDA kernels, the stub model and synthetic scenes
├── tools/prepare_model.py      Exports YOLO26 with a separately installed Ultralytics tool
├── pkg/holoscan-yolo26/        Debian packaging, entered when PKG_holoscan_yolo26 is ON
└── tests/
    ├── host/                   SDK-free tests, also a project of their own
    └── installed_consumer/     Uses the installed package
```

The layout follows the collection's other modules: public headers under `include/`, one library
per public target, and the package config generated by the module itself, so that a plain
`cmake --install` produces a usable package. The Debian packaging keeps the Holoscan CLI template's
`holohub_configure_deb()` and `PKG_holoscan_yolo26` switch, so `holoscan package` works unchanged.

## Build and package boundary

| | |
| --- | --- |
| Build contexts | Top-level CMake project, or included by another project (`add_subdirectory()`, `FetchContent`, the repository root); it is not built inside the SDK tree |
| Options | Top level: `BUILD_TESTING` (`OFF`), `BUILD_SHARED_LIBS` (`ON`). Included: `HOLOSCAN_YOLO26_BUILD_TESTING` (`OFF`), always shared, the includer's `BUILD_TESTING` and `BUILD_SHARED_LIBS` left alone. Both: `HOLOSCAN_YOLO26_BUILD_OVERLAY` (`ON`; `OFF` when the repository root's `HOLOSCAN_ZOZO_MODULES_OPERATORS` lacks `Yolo26OverlayOp`), `PKG_holoscan_yolo26` (`OFF`) |
| Public targets | `holoscan::yolo26` (`libholoscan_yolo26.so.1`), `holoscan::yolo26_overlay` (`libholoscan_yolo26_overlay.so.1`) |
| Include root | `include/`, installed to `<prefix>/include` |
| Package | `<prefix>/lib/cmake/holoscan-yolo26/holoscan-yolo26-config.cmake`, `SameMajorVersion`; sets `holoscan-yolo26_PREPARE_MODEL` |
| Consumer form | `find_package(holoscan-yolo26 [COMPONENTS overlay])`; the install prefix on `CMAKE_PREFIX_PATH`, or `/usr` from the Debian package |
| Installed tool | `<prefix>/share/holoscan-yolo26/prepare_model.py` |
| Debian package | `holoscan-yolo26`, all install rules, prefix `/usr`; depends on `holoscan (>= 5.0.0)` |
| External dependencies | Holoscan SDK 5.0 (`core`, `sensor_io`, `inference`; `visualization` for the overlay; `testing` for the tests), the CUDA runtime, TensorRT 10 through HoloInfer |
| Platforms | x86_64; aarch64 (Jetson Thor, JetPack 7) |
| Test labels | `yolo26` on all; `gpu` for the GPU tests; `host` for the SDK-free tests |

## Conventions

- Code lives in `holoscan::yolo26`. Inside it, write the SDK's test harness as
  `holoscan::testing::...`; the tests' own helpers are `holoscan::yolo26::test`.
- Public headers carry only SDK, CUDA runtime and standard types; HoloInfer stays private to
  `src/yolo26_detection_op.cpp`. `letterbox.hpp`, `stub_model.hpp` and `synthetic_scene.hpp` need no
  CUDA, so `tests/host/` builds their sources without it.
- Device code uses CCCL headers available in CUDA 13.0 (CUB's `BlockScan`), so the module also
  builds with JetPack 7's toolkit.
- The kernels are compiled without FMA contraction (`-fmad=false`), and the host code that computes
  with them without `-ffp-contract`, so the tests compare them with host evaluations bit for bit.
- The repository holds no YOLO26 weights or Ultralytics code, and must not: the model is AGPL-3.0.
  `tools/prepare_model.py` only runs the user's own `yolo` command. Tests use the stub model.
- A new setting or behavior of an operator needs a case in `yolo26_operators`; a change to a kernel,
  a case in `yolo26_letterbox` or `yolo26_decode`.
